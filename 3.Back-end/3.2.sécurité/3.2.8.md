# 📘 3.2.8 — Première Policy sur les articles et comparaison avec les Gates

> Tutoriel 3.2.8 issu de l’autoformation : 3.2. Sécurité et accès à l’admin (N1).

---

## 1️⃣ Introduction

Dans les tutoriels précédents, tu as :

* sécurisé `/admin` avec le middleware **`auth`** (3.2.3),
* mis en place les profils **Admin / Auteur** via `is_admin` (3.2.4),
* affiché le profil dans l’interface (3.2.5),
* codé les règles métiers avec des **Gates** :

  * dans les **contrôleurs** (`store`, `destroy`) (3.2.6),
  * dans les **vues Blade** avec `@can` / `@cannot` (3.2.7).

Les Gates fonctionnent bien, mais :

> Quand les règles d’autorisation sont liées à un **modèle précis** (ici, `Article`),
> Laravel propose un outil plus structuré : les **Policies**.

Dans ce tutoriel, tu vas :

* créer une **Policy pour les articles**,
* y déplacer la règle de **suppression** qui était dans la Gate,
* l’utiliser dans un **contrôleur** et une **vue Blade**,
* comparer ce fonctionnement avec les Gates.

---

## 2️⃣ Objectif pédagogique

À la fin de ce tutoriel, tu seras capable de :

* générer une **Policy Laravel** liée à un modèle (`Article`) ;
* implémenter la méthode **`delete`** dans cette Policy en suivant la règle métier (Admin / Auteur) ;
* utiliser `authorize('delete', $article)` dans un contrôleur ;
* utiliser `@can('delete', $article)` dans une vue Blade ;
* expliquer la **différence** entre Gates et Policies.

---

## 3️⃣ Pré-requis

Tu dois déjà avoir :

* un projet Laravel (projet fil rouge) fonctionnel ;

* l’authentification Laravel UI + `/admin` protégé (3.2.2, 3.2.3) ;

* le champ `is_admin` sur la table `users` + cast booléen (3.2.4) ;

* l’affichage du rôle (Admin / Auteur) dans l’interface (3.2.5) ;

* des Gates définies pour les articles dans `AuthServiceProvider` (3.2.6) :

  * `create-article`,
  * `delete-article`,

* les boutons “Ajouter” / “Supprimer” protégés via `@can` dans les vues (3.2.7) ;

* un modèle `Article` avec un champ `user_id` (propriétaire de l’article).

---

## 4️⃣ Rappel : Gates vs Policies (version courte)

* Une **Gate** est une règle d’autorisation **globale** :

  * définie dans `AuthServiceProvider` avec `Gate::define()` ;
  * souvent utilisée pour des actions **simples** ou **transversales**.

* Une **Policy** est une classe dédiée à un **modèle** :

  * par exemple `ArticlePolicy` pour le modèle `Article` ;
  * contient des méthodes comme `view`, `create`, `update`, `delete`, etc. ;
  * regroupe **toute la logique d’autorisation** autour de ce modèle.

Dans ce tutoriel, tu vas :

> prendre la règle “qui peut supprimer un article ?”
> et la déplacer d’une **Gate** vers une **Policy**.

---

## 5️⃣ Étapes guidées (N1 — Imiter)

---

### 🧩 Étape 1 — Générer la Policy pour les articles

Tu vas créer une Policy liée au modèle `Article`.

**Action**

1. Ouvre un terminal dans le dossier de ton projet :

   ```bash
   cd chemin/vers/ton/projet-blog
   ```

2. Génère une Policy `ArticlePolicy` liée au modèle `Article` :

   ```bash
   php artisan make:policy ArticlePolicy --model=Article
   ```

3. Laravel crée un fichier dans :

   ```text
   app/Policies/ArticlePolicy.php
   ```

4. Ouvre ce fichier dans ton éditeur de code.

#### ▶ Résultat attendu

* Le fichier `app/Policies/ArticlePolicy.php` existe.
* Il contient une classe `ArticlePolicy` avec plusieurs méthodes vides (ou commentées) : `viewAny`, `view`, `create`, `update`, `delete`, etc.

#### 💡 Explication

La commande `make:policy` te fournit une **structure de classe** :

* déjà liée au modèle `Article` (via le `--model=Article`),
* prête à recevoir les règles d’autorisation (une méthode par type d’action).

---

### 🧩 Étape 2 — Implémenter la méthode `delete` dans la Policy

Tu vas recopier la **même logique métier** que dans la Gate `delete-article`.

Rappel métier :

* **Admin** → peut supprimer **n’importe quel article** ;
* **Auteur** → peut supprimer **uniquement ses propres articles**.

**Action**

1. Dans `ArticlePolicy.php`, repère (ou décommente) la méthode `delete` :

   ```php
   public function delete(User $user, Article $article): bool
   {
       //
   }
   ```

2. Implémente la logique suivante :

   ```php
   use App\Models\User;
   use App\Models\Article;

   class ArticlePolicy
   {
       // ...

       public function delete(User $user, Article $article): bool
       {
           // Admin → peut supprimer n’importe quel article
           if ($user->is_admin) {
               return true;
           }

           // Auteur → peut supprimer seulement ses propres articles
           return $article->user_id === $user->id;
       }
   }
   ```

3. Vérifie que les `use` en haut du fichier sont présents :

   ```php
   use App\Models\User;
   use App\Models\Article;
   ```

#### ▶ Résultat attendu

* La méthode `delete()` de `ArticlePolicy` contient la même règle que ta Gate `delete-article`.

#### 💡 Explication

Tu as maintenant une **version “Policy”** de ta règle de suppression :

* elle vit dans une **classe dédiée** au modèle `Article` ;
* elle sera utilisée par Laravel quand tu appelleras `authorize('delete', $article)`
  ou `@can('delete', $article)`.

---

### 🧩 Étape 3 — Vérifier l’enregistrement de la Policy

Laravel doit savoir quelle Policy utiliser pour le modèle `Article`.

**Action**

1. Ouvre le fichier :

   ```text
   app/Providers/AuthServiceProvider.php
   ```

2. En haut, vérifie que les `use` sont présents :

   ```php
   use App\Models\Article;
   use App\Policies\ArticlePolicy;
   ```

3. Dans la propriété `$policies`, vérifie que tu as au moins :

   ```php
   protected $policies = [
       Article::class => ArticlePolicy::class,
   ];
   ```

> Selon ta version de Laravel et la commande `make:policy`, cette ligne peut être déjà générée. Le but est de **la vérifier**.

#### ▶ Résultat attendu

* `Article::class` est bien associé à `ArticlePolicy::class` dans `$policies`.

#### 💡 Explication

La propriété `$policies` dit à Laravel :

> “Pour le modèle `Article`, utilise la classe `ArticlePolicy` pour les autorisations.”

C’est ce lien qui permet d’écrire ensuite `authorize('delete', $article)` sans préciser la Policy.

---

### 🧩 Étape 4 — Utiliser la Policy dans le contrôleur (méthode `destroy`)

Tu vas maintenant remplacer l’usage de la Gate `delete-article` par la **Policy** dans ton contrôleur.

**Action**

1. Ouvre ton contrôleur d’articles, par exemple :

   ```text
   app/Http/Controllers/ArticleController.php
   ```

2. Repère la méthode `destroy()` qui ressemblait à ceci (après 3.2.6) :

   ```php
   public function destroy(Article $article)
   {
       if (! Gate::allows('delete-article', $article)) {
           abort(403);
       }

       $article->delete();

       return redirect()->back()->with('status', 'Article supprimé avec succès.');
   }
   ```

3. Remplace le bloc de vérification par un appel à `$this->authorize()` :

   ```php
   public function destroy(Article $article)
   {
       $this->authorize('delete', $article);

       $article->delete();

       return redirect()->back()->with('status', 'Article supprimé avec succès.');
   }
   ```

4. Garde l’`use` de `Article` en haut du fichier.
   Tu n’as plus besoin de la façade `Gate` pour cette méthode, mais tu peux la garder si elle sert ailleurs.

#### ▶ Résultat attendu

* La méthode `destroy()` utilise maintenant la Policy :

  * si l’utilisateur **a le droit** → suppression + redirection,
  * s’il **n’a pas le droit** → exception 403 **automatique** (gérée par `authorize()`).

#### 💡 Explication

* `$this->authorize('delete', $article)` :

  * va chercher la **Policy associée** au modèle `Article`,
  * appelle la méthode `delete(User $user, Article $article)` de cette Policy,
  * si la méthode renvoie `false` → **403 Forbidden** automatique.

Tu n’as plus besoin d’appeler `Gate::allows()` ni `abort(403)` à la main.

---

### 🧩 Étape 5 — Utiliser la Policy dans la vue avec `@can('delete', $article)`

Dans 3.2.7, tu utilisais déjà :

{% raw %}
```php
@can('delete-article', $article)
    {{-- bouton Supprimer --}}
@endcan
```
{% endraw %}

Tu vas maintenant utiliser le **nom de la méthode de Policy** : `delete`.

**Action**

1. Ouvre la vue d’admin qui liste les articles, par exemple :

   ```text
   resources/views/admin/articles/index.blade.php
   ```

2. Repère le bloc qui affiche le bouton “Supprimer” :

   {% raw %}
```php
   @can('delete-article', $article)
       <form action="{{ route('admin.articles.destroy', $article) }}" method="POST">
           @csrf
           @method('DELETE')
           <button type="submit" class="btn btn-danger btn-sm">
               Supprimer
           </button>
       </form>
   @endcan
   ```
   {% endraw %}

3. Adapte-le avec la Policy **et** des classes Tailwind :

   {% raw %}
```php
   @can('delete', $article)
       <form action="{{ route('admin.articles.destroy', $article) }}" method="POST"
             onsubmit="return confirm('Confirmer la suppression ?')">
           @csrf
           @method('DELETE')
           <button type="submit"
                   class="inline-flex items-center rounded bg-red-600 px-3 py-1 text-xs font-semibold text-white hover:bg-red-700">
               Supprimer
           </button>
       </form>
   @endcan
   ```
   {% endraw %}

4. Si tu utilises aussi `@cannot` pour afficher un message, adapte également :

   {% raw %}
```php
   @cannot('delete', $article)
       <span class="ml-2 text-xs text-gray-500">
           Vous ne pouvez pas supprimer cet article.
       </span>
   @endcannot
   ```
   {% endraw %}

#### ▶ Résultat attendu

* Le bouton “Supprimer” est maintenant contrôlé par la Policy (`delete`) et non plus par la Gate `delete-article`.
* Le comportement côté interface **ne change pas** pour l’utilisateur.

#### 💡 Explication

* `@can('delete', $article)` appelle la Policy :

  * Laravel trouve `ArticlePolicy` grâce au mapping dans `$policies`,
  * il exécute `ArticlePolicy::delete($user, $article)`.

Tu réutilises donc **exactement la même règle** côté contrôleur et côté vue.

---

### 🧩 Étape 6 — (Optionnel) Désactiver la Gate `delete-article`

Pour éviter la confusion, tu peux **supprimer** (ou commenter) la Gate `delete-article` dans `AuthServiceProvider`.

**Action**

1. Ouvre `app/Providers/AuthServiceProvider.php`.

2. Dans la méthode `boot()`, tu dois voir quelque chose comme :

   ```php
   Gate::define('create-article', function ($user) {
       return $user->is_admin === false;
   });

   Gate::define('delete-article', function ($user, Article $article) {
       // logique de suppression...
   });
   ```

3. Tu peux maintenant **supprimer ou commenter** la partie `delete-article`, puisque la Policy s’en occupe :

   ```php
   public function boot(): void
   {
       $this->registerPolicies();

       Gate::define('create-article', function ($user) {
           return $user->is_admin === false;
       });

       // La logique de suppression est maintenant gérée par ArticlePolicy::delete()
       // Gate::define('delete-article', function ($user, Article $article) {
       //     ...
       // });
   }
   ```

4. Sauvegarde le fichier.

#### ▶ Résultat attendu

* La Gate `delete-article` n’est plus utilisée.
* La suppression repose **uniquement** sur la Policy.

#### 💡 Explication

Tu gardes :

* la Gate `create-article` (pratique pour une règle simple, non liée à un modèle),
* la Policy `ArticlePolicy` pour les règles liées au modèle `Article` (ici, `delete`).

---

### 🧩 Étape 7 — Tester les scénarios (Auteur / Admin)

Comme dans 3.2.6 et 3.2.7, tu dois vérifier que **rien n’a changé côté comportement** :

* seul **l’emplacement de la logique** a changé (Gates → Policy).

**Action**

1. Lance le serveur :

   ```bash
   php artisan serve
   ```

2. **Scénario Auteur**

   * Connecte-toi avec le compte Auteur (`is_admin = 0`).

   * Va sur la liste des articles dans l’admin.

   * Vérifie que :

     * le bouton “Supprimer” est visible **seulement** pour les articles qu’il a écrits ;
     * il disparaît pour les articles des autres.

   * Essaie de supprimer un article :

     * **son** article → OK ;
     * l’article de quelqu’un d’autre → 403 Forbidden (si tu forces l’URL, par exemple).

3. **Scénario Admin**

   * Connecte-toi avec le compte Admin (`is_admin = 1`).
   * Va sur la liste des articles.
   * Vérifie que :

     * le bouton “Supprimer” est visible **pour tous** les articles ;
     * la suppression fonctionne pour tous.

#### ▶ Résultat attendu

* Le comportement est identique à celui avec les Gates.
* Tu confirmes que la Policy fonctionne correctement dans le contrôleur et la vue.

## 6️⃣ Comparaison rapide : Gates vs Policies

| Aspect                         | Gates                                      | Policies                                                 |
| ------------------------------ | ------------------------------------------ | -------------------------------------------------------- |
| Emplacement du code            | `AuthServiceProvider`                      | Classe dédiée dans `app/Policies`                        |
| Lien avec un modèle            | Optionnel, à gérer soi-même                | Directement liée à un modèle (`Article`)                 |
| Organisation                   | Règles “éparpillées”                       | Règles regroupées par modèle                             |
| Utilisation dans le contrôleur | `Gate::allows('action', $objet)` + `abort` | `$this->authorize('action', $objet)`                     |
| Utilisation dans les vues      | `@can('gate-name', $objet)`                | `@can('method-name', $objet)`                            |
| Cas d’usage typique            | Règles simples ou transversales            | CRUD complet d’un modèle (view, create, update, delete…) |

👉 **Idée à retenir** :

* Pour 1 ou 2 petites règles ponctuelles : **Gates** suffisent.
* Pour tout ce qui concerne un **modèle précis** (comme `Article`) :
  il est plus propre de créer une **Policy**.

## 7️⃣ Vérification & erreurs fréquentes

| Problème                                              | Cause probable                                       | Piste de solution                                                                                                 |
| ----------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Erreur “Class ArticlePolicy not found”                | `use App\Policies\ArticlePolicy;` manquant           | Ajoute l’import en haut de `AuthServiceProvider`.                                                                 |
| Erreur “Target class [ArticlePolicy] does not exist”  | Mapping `$policies` incorrect                        | Vérifie : `Article::class => ArticlePolicy::class`.                                                               |
| `authorize('delete', $article)` lève toujours 403     | Logique de la Policy incorrecte                      | Revois la méthode `delete()` (Admin / Auteur, `user_id`).                                                         |
| `@can('delete', $article)` ne change rien dans la vue | Mauvais article passé en paramètre ou vue incorrecte | Vérifie la variable `$article` et le fichier Blade édité.                                                         |
| Comportement différent entre vue et contrôleur        | Mélange Gate/Policy ou noms d’actions différents     | Harmonise : `authorize('delete', $article)` et `@can('delete', $article)` doivent pointer sur **la même** Policy. |

## 8️⃣ Lien avec le projet fil rouge

Avec cette Policy, la sécurité de ton blog Laravel devient plus :

* **structurée** : toutes les règles liées à `Article` sont dans `ArticlePolicy` ;
* **lisible** : un formateur ou un autre développeur voit rapidement :

  * qui peut créer,
  * qui peut mettre à jour,
  * qui peut supprimer un article.

Pour la version **V6 — Sécurité et accès à l’admin** :

* tu as maintenant :

  * un espace `/admin` protégé,
  * des profils Admin / Auteur visibles,
  * des règles d’accès **cohérentes** sur les articles,
  * une logique d’autorisation proprement centralisée.

En N3, une version “pro” pourrait :

* ajouter d’autres méthodes à la Policy (`update`, `restore`, etc.) ;
* utiliser un système avancé de rôles/permissions (par ex. Spatie) tout en gardant la structure centralisée des Policies.
